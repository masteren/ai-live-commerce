# 学习笔记 10:代码审查发现的 3 个 bug(都是「先读后写」)

这三个 bug 当时测试全部通过——**测试只能证明「想到的情况」没问题**。都是先写脚本复现、再修、再把复现脚本变成测试。

## bug 1:同一用户并发下单 → 重复订单
- 现象:购物车里 1 件商品,5 个下单请求同时到达 → 5 张订单,库存 30→25。
- 原因:`checkout` 先 SELECT 购物车,最后才 DELETE;5 个请求都读到了同一份购物车。
- 修正(`app/routers/orders.py`):先「认领」购物车——`DELETE ... WHERE id=? AND quantity=?`,**影响行数不是 1 就回滚**。后到的请求删不到行,自然失败。
- 和超卖的修法是同一个思想:**不相信之前读到的值,让数据库在一条语句里完成判断**。

## bug 2:并发「加入购物车」→ 同一商品多行,之后永远 500
- 原因:先 SELECT 看有没有,再 INSERT;而且表上没有唯一约束(DB2x 学过的 UNIQUE)。
- 修正:① `(user_id, product_id)` 加唯一约束(迁移里先合并已有的重复行,否则加约束会失败)② 先 INSERT,撞到唯一约束(IntegrityError)再做 `UPDATE quantity = quantity + n`。
- **只在 MySQL 上出现的坑**:一开始写成「先 UPDATE,0 行再 INSERT」,在 SQLite 上测试全过,在 MySQL 上间歇性**死锁**(多个事务各自拿到间隙锁再互相等待)。在本地 Docker 的 MySQL 上跑测试才发现 → 这就是开发环境要接近正式环境的原因。

## bug 3:旧数据库被标记为「最新版」
- 原因:`migrate.py` 对没有版本记录的旧库执行 `stamp head`。加了第二个迁移后,旧库被记成最新,但实际没有新列。
- 修正:记录为「引入 Alembic 时的版本」(BASELINE),之后的迁移照常执行;比基准更旧的库直接报错停止,不悄悄继续。

## 面试怎么讲
「自分で書いた並行テストで売り越しを見つけて直した後、コードを見直して、同じ種類の問題(読んでから書く)が注文の二重送信とカート追加にも残っていることを再現テストで確認し、DB の制約と条件付きの書き込みで直しました。MySQL でだけ起きるデッドロックも、ローカルの MySQL でテストして見つけました。」
