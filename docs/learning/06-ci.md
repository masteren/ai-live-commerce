# 学习笔记 06:CI(GitHub Actions)

## 1. 做了什么
`.github/workflows/ci.yml`:每次 push 到 GitHub(或开 Pull Request)时,GitHub 的服务器自动运行 3 个任务:
| 任务 | 内容 |
|---|---|
| unit-sqlite | Python 3.12 / 3.13 两个版本各跑一遍 pytest |
| unit-mysql | 启动真实的 MySQL 8.4(utf8mb4_bin),用 `TEST_DATABASE_URL` 让同一套 pytest 跑在 MySQL 上 → 验证行锁、迁移、字符集 |
| e2e | 真的启动服务器,跑 test_e2e.py(含 WebSocket) |

本机没装 Docker 也没关系:MySQL 的验证在 GitHub 的服务器上完成。

## 2. 为什么重要(面试会问)
- **防止「我这里能跑」**:在干净的环境里从零安装依赖再测试,能发现漏写进 requirements.txt 的包。
- **防止改坏**:任何改动都自动跑 80 项测试,失败就会在 GitHub 上显示红叉。
- **同一套测试换数据库**:测试代码不写死 SQLite,通过环境变量切换 → 体现「配置与代码分离」(和 .env 是同一个思想)。

## 3. 第一次运行时 CI 发现的问题(真实案例,面试可以讲)
第一次 push 后 CI **失败**了,原因有两个:
1. **`No module named 'app'`**:本地一直用 `python -m pytest`(会把当前目录加入 import 路径),而 CI 和 README 写的是 `pytest`(不会加)。→ 在 `pytest.ini` 加 `pythonpath = .` 解决。**本地能跑、别人的环境跑不了**的典型例子,正是 CI 要防的问题。
2. **Python 3.9 在 CI 环境里已经没有了**(2025 年 10 月结束支持)。→ CI 改为 3.12 / 3.13。

修正后 4 个任务全部通过,其中 **unit-mysql 在真实的 MySQL 8.4 上跑通了全部单元测试**(行锁、utf8mb4_bin、迁移)——本机没装 Docker 也完成了 MySQL 的验证。

- 本地 venv 已用 uv 升级到 Python 3.12(2026-11-13)。旧环境备份在 `venv-py39.bak/`(已加入 .gitignore,确认没问题后可以删除)。
