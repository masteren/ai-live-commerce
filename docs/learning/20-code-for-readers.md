# 学习笔记 20:让代码「给别人看」也没问题

这一轮没有加功能,做的是三件「别人打开代码或 App 时会注意到」的事。

## 1. 注释和日志统一成日文
- 服务器代码(`app/`)里原来大约一半注释是中文(早期写的),一半是日文。日志里还有「LLM の返答を解釈できません,降级为规则回复」这种半日半中的。全部改成日文。
- 怎么找的:写了个小脚本,找「有汉字但没有假名」的行。日文的句子几乎一定有平假名或片假名,中文没有,所以这个方法很准。
- 顺便发现 `models.py` 里密码格式的注释还是旧的(`salt$hash`),实际早就改成 `pbkdf2_sha256$次数$盐$哈希` 了 —— **注释不会报错,所以过时了也没人发现**。翻译时把整段读一遍,是检查注释是否过时的好机会。

## 2. iOS:开发者设置放到下一层
账号页原来直接显示「接続先サーバ」和一段写给开发者的说明。现在账号页只显示「バージョン」和「開発者向け設定 ›」,点进去才是服务器地址。功能没变,只是不让普通用户第一眼看到。

## 3. 网页:HTML / CSS / JS 分开,加上 Content-Security-Policy
### 拆分
| 之前 | 之后 |
|---|---|
| `index.html` 848 行(HTML+CSS+JS) | `index.html` 226 行、`css/live.css` 249 行、`js/live.js` 376 行 |
| `admin.html` 200 行 | `admin.html` 42 行、`css/admin.css`、`js/admin.js` |
| `vrm.js` | `js/vrm.js` |

### CSP 是什么
服务器在返回页面时加一个响应头 `Content-Security-Policy`,告诉浏览器「这个页面只准执行哪里来的脚本」。这次的规则是:**只执行本站 `/static/js/` 下的文件,页面里直接写的 `<script>` 和 `onclick="..."` 一律不执行**。
- 为什么有用:就算哪天出现 XSS 漏洞(别人往页面里塞了一段脚本),浏览器也会拒绝执行。这是在「输出时转义」之外的第二道防线。
- 为什么必须先拆分:原来的脚本就写在 HTML 里,加了 CSP 连自己的脚本也会被拦。所以要先把脚本搬到单独的文件,再把 `onclick="..."`(3 处在管理页、2 处在支付弹窗)改成在 JS 里绑定。
- 一个例外:3D 模型用的 `importmap`(告诉浏览器 `three` 这个模块在哪)按规范只能写在页面里。所以服务器启动时计算它内容的 SHA-256,只允许「内容完全一样」的这一段(`app/main.py` 的 `_content_security_policy`)。内容改了会自动重新计算。
- style 的规则放宽了(`'unsafe-inline'`),因为页面到处用 `style="..."`;样式被注入的危害远小于脚本。

### 测试时踩到的坑
浏览器测试脚本用的 `page.waitForFunction()`,内部会把函数当字符串在页面里执行 —— 被 CSP 拦住了(说明 CSP 确实在起作用)。改成从外面反复调用 `page.evaluate()` 来等待。

## 追记:最后回归时 iOS 测试偶尔卡住
全部 iOS 测试一起跑时,有时某一项会超过时间限制。查的方法和结论:
- **Xcode 在超时时会抓一份现场记录(spindump)**。看 App 的主线程:在等消息、是空闲的 → App 没有卡死。看测试程序:卡在「点击前,等 App 画面静止」这一步。
- 第一次卡在注册弹窗的密码框:画面上有 iOS 系统的密码自动填充提示条。→ 自动测试时把密码框换成普通输入框(只在带 `--ui-testing` 启动时;正常使用仍是隐藏输入)。
- 第二次换了一项测试卡住。**把测试时的录屏逐帧取出来看,260 秒里画面一动不动**,连按 Home 键都没反映 → 是模拟器的显示冻结了。重启模拟器后全部通过。
- 教训:测试失败先分清「App 的问题」还是「测试环境的问题」。现场记录和录屏比猜测可靠。
